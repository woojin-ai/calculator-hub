### 🔴 4-A. `/about` 본문 자기모순 (planning이 부수 발견, 마스터가 라이브 확인)
라이브 `/about`이 **같은 화면에서 자기모순**이었다. 마스터가 직접 긁은 원문:
> "…라이브 계산기 **5개** … 라이브 계산기 **4개** … 라이브 계산기 **3개** … 라이브 계산기 **4개** … 현재 바로 사용할 수 있는 계산기는 다음과 같습니다. 만 나이 계산기 — … D-Day 계산기 — … BMI 계산기 — … **급여·대출 카테고리 계산기는 현재 준비 중이며**, 순차적으로 추가될 예정입니다."

→ **`calculators` 데이터 파생으로 교체.** 다시 낡을 수 없는 구조가 요구사항의 핵심이었다.

### 4-B. `metaDescription` 선택 필드 신설 — 화면 문자열 분리
두 팀이 **독립적으로 같은 리스크**를 짚었다: 문제의 문자열들은 meta 전용이 아니라 **화면에 렌더된다.** 마스터가 코드로 확인:
- `calculator.shortDescription` → `app/calculator/[slug]/page.tsx:70`(meta) + `:129`(상세 리드문) + `components/CalculatorCard.tsx:36`(카드)
- `categoryInfo[].description` → 카테고리 `page.tsx`(meta) + `CategoryPage.tsx:34` + `app/page.tsx:121`(홈 4단 그리드) + `app/about/page.tsx:65`

즉 desc를 90자로 늘리면 **홈 그리드 카드 본문이 3배**가 된다. planning은 이걸 "이번 건 최대 리스크"로, marketing은 "분리 안 하면 홈 레이아웃 회귀 검수가 QA 필수"로 올렸다.

→ **마스터 판정: 선택 필드 `metaDescription?` 신설, `metadata.description`에서만 `metaDescription ?? shortDescription`(계산기)·`?? description`(카테고리). 화면 렌더 지점은 기존 필드 유지.** 이 결정으로 **레이아웃 리스크가 구조적으로 0**이 되고, planning이 올린 "375px에서 90자 리드가 첫 카드를 밀어내는가"라는 디자인 질의도 **소멸**했다(디자인팀 호출 불필요).

**JSON-LD는 손대지 않았다** — 의도적 결정이다. 구조화 데이터의 description은 화면에 보이는 설명과 일치시키고, meta는 SERP 스니펫용으로 분리한다.
