## 4) 기획팀 판정 — 앵커 목록 `0%`·`75%`는 자릿수 맞춤 대상 **아님** (변경 0건)

개발팀이 범위 밖 사안을 **임의 수정하지 않고 보고**해서 열린 건. 판정 근거(기획팀이 원문 직독):

- 자릿수 맞춤의 실제 기준은 **"정확값이냐"가 아니라 "동일 계열 계단 리스트에 속하느냐"**다.
  표준의 `50.0%` 예시의 원값(0.5)도 **똑같이 정확값**이다 → "정확히 떨어지면 `.0` 생략" 해석은 그 예시를 스스로 깬다.
- 앵커 A~H는 분모가 36 / 36캡 / **24**로 제각각인 **독립 케이스 체크리스트**. 특히 G는 유일하게 분모 24라 36 계열의 형제가 아니다.
- 표준 §2-3이 `.0`의 유무를 **"반올림값 vs 정확값" 신호**로 쓰고 있다(`18 ÷ 24 = 75%`만 `=` 허용). `75.0%`로 바꾸면 그 신호를 파괴 — 미관이 YMYL 엄밀성을 이길 이유가 없다.
- 면제 `0%`는 §2-2에 **전용 분기 행**이 이미 있고, 라이브 정본(`lib/blog.ts` SET B)에도 `0.0%`가 아니라 `잔존 0 → 면제` 형태로 이미 박혀 있다. 앵커만 다르게 가면 표준 내부 모순.

**부수 소득**: 기획팀이 `lib/blog.ts` 전수 확인 → **"정수 비율 + 소수 형제 동거" 리스트는 라이브에 0건**. 우선순위 격상 없음.
또 실효수익률 리스트의 `3.5%`(형제는 2자리)는 **의도된 것**(본문이 명목금리 3.5%와의 일치를 논지로 삼음) → 손대지 말 것을 표준에 남기도록 권고받음.

## 11) 운영 표준 (이번 회차 추가)

- **[신규 ㉵ — 중요] 인계 요약이 아니라 원본 스펙에서 작업 목록을 옮겨라.**
  오늘 FAIL-1의 원인은 전날 팀로그 요약(`"15개 토큰 잔여"`)이 **비수치 요구사항(주석 1줄)을 이미 탈락시킨 상태**였고, 마스터가 그 요약을 그대로 브리프로 옮긴 것이다.
  **요약은 숫자를 보존하고 조건을 잃는다.** 이월 항목을 착수할 때는 반드시 **원본 스펙 행을 열어 대조**해라.
- **[신규 ㉶] 공유 작업 트리에서는 파일이 아니라 헝크를 커밋 단위로 삼아라.**
  동시 세션이 같은 파일을 편집 중일 때 `git add <파일>`은 남의 미검증 작업을 라이브로 밀어낸다.
  **의미 기준 필터(내 변경의 형태를 정의) + 개수 게이트(기대치와 다르면 throw) + `git apply --cached`**로 인덱스에만 올려라. 워킹트리는 건드리지 않는다.
- **[강화 ⓔ — 3회째 적중] "전 항목 균일 실패"는 자기 검증도구 결함의 지표다.**
  오늘은 치환 방향을 반대편 파일에 적용해 10/10 FAIL이 났다. 데이터를 의심하기 전에 **도구의 인자 순서·방향부터** 확인해라.
- **[유지]** 팀 보고는 마스터 검증의 입력이지 결론이 아니다(㉴ — 오늘 QA의 FAIL 보고도 직접 재현한 뒤 수용했다) ·
  라이브를 고치면 그 라이브를 만든 스펙도 함께(㉲) · 스크래치는 **Write + node/npx tsx**(heredoc 금지) ·
  검증 결과에 **본 파일의 시각**을 붙여라(㉳ — 오늘 QA가 mtime을 명시해 08-01 같은 낡은 스냅샷 사고 없었다).
