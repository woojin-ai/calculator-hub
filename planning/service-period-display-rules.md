## 1. 현재 표시 경로 (실측 Read 결과)

### 1-1. 주 화면 — 근속연수·근무일수 계산기

`components\ServicePeriodCalculator.tsx`에서 `years`/`months`/`days`가 화면 문자열이 되는
지점은 **정확히 3곳**이다. [확인]

| # | 위치 | 형태 | 성격 |
|---|---|---|---|
| A | `components\ServicePeriodCalculator.tsx:145-168` | 히어로 3세트 분리 렌더. 숫자 `text-4xl font-bold text-brand-accent sm:text-[2.5rem]` + 단위 `text-base` | **시각적 대표값** |
| B | `components\ServicePeriodCalculator.tsx:143` | `aria-label={\`근속기간 ${result.years}년 ${result.months}개월 ${result.days}일\`}` | **스크린리더 낭독값** |
| C | `components\ServicePeriodCalculator.tsx:20` (`getResultSummary`, 14-21행) | `...근속기간은 ${result.years}년 ${result.months}개월 ${result.days}일입니다.` → 173행에서 렌더 | **동적 요약 문구** |

- 세 곳 모두 `result.years`/`months`/`days`를 **가공 없이 그대로** 문자열에 넣는다. 포맷 함수·
  클램프·조건 분기 **없음**. [확인]
- 따라서 라이브의 `26년 1개월 -1일`은 A(히어로), B(aria-label), C(요약 문구) **3곳에 동시 노출**된다.
  스크린리더 사용자도 "마이너스 일"을 그대로 듣는다. [확인]
- 값의 출처: `lib\service-period.ts:84-101` (`calculateServicePeriod`의 years/months/days 분해 +
  단일 borrow 블록). 표시부에는 버그가 없다 — 표시부는 엔진 출력을 정직하게 그리고 있을 뿐이다. [확인]

### 1-2. 같은 값을 쓰는 **두 번째 화면이 존재한다** (이슈)

Grep 결과, 동일한 `years`/`months`가 **퇴직금 계산기에도 표시**된다. [확인]

- `lib\severance.ts:117-132` — `calculateSeverance`가 `calculateServicePeriod`를 그대로 재사용해
  `service.years/months/days`로 넘긴다. **즉 같은 borrow 버그를 그대로 물려받는다.**
- `components\SeverancePayCalculator.tsx:394` (정상 결과 카드 Tier②)
- `components\SeverancePayCalculator.tsx:424` (1년 미만 미해당 카드)
  - 두 곳 모두 문자열: `` `${totalDays}일 (근속 ${years}년 ${months}개월)` ``

**이슈 판정 — 두 가지가 겹쳐 있다.**

1. **표시 규칙이 두 곳에 흩어져 있다.** 근속기간 조립 규칙이 `ServicePeriodCalculator`(3부분,
   년/개월/일)와 `SeverancePayCalculator`(2부분, 년/개월)에 **각각 하드코딩**돼 있고,
   공용 포맷 유틸이 없다. 앞으로 규칙이 바뀔 때마다 4개 지점(A/B/C + 퇴직금 2행)을 개별 수정해야 한다.
2. **퇴직금 화면은 `days`를 버려서 음수가 안 보이지만, `months`는 오염된 채로 보인다.**
   버그가 `days`를 음수로 만들면서 `months`를 1 깎는 구조이므로(`lib\service-period.ts:88-97`),
   퇴직금의 `근속 26년 1개월` 역시 **수정 후 값이 바뀔 수 있다.** 음수가 안 보인다고 무사한 화면이 아니다.

**→ 개발팀 요청 (표시 규칙 관점):**
- 티켓 #2의 QA/회귀 범위에 **퇴직금 계산기 결과 카드 2행(394·424)을 반드시 포함**할 것.
  근속기간 계산기만 보고 종결하면 퇴직금 화면의 `개월` 오차가 남는다.
- (선택, 개발팀 판단) 근속기간 문자열 조립을 `lib\service-period.ts`의 공용 포맷 함수로 모으는 것을
  권장한다. 다만 **이번 티켓은 버그 수정이 목적이므로 리팩터링을 강제하지 않는다** —
  범위가 커지면 별도 티켓으로 분리할 것.

## 2. 0 값 표시 규칙 — **변경 불필요 (이미 확정·구현됨)**

### 2-1. 판정

버그 수정 후 정상적으로 발생하는 `0년 0개월 5일`, `1년 0개월 0일`, `0년 3개월 0일`,
`0년 0개월 1일`(입사 당일 퇴사) 형태는 **이미 스펙에 명시돼 있고 코드도 그대로 구현돼 있다.**
신규 규칙이 아니다. **개발팀 추가 작업 없음.**

- 스펙 근거: `design\service-period-calculator-ui-spec.md` §3-2 (218-219행) — [확인]
  > 0 표기: `0년 0개월 1일`(앵커 E)처럼 0인 자리도 **생략하지 않고 표시**한다(엔진이 항상 3부분을
  > 주므로). "0년"을 감추면 위계가 흔들리고 앵커 검증도 어긋난다.
- 코드 근거: `components\ServicePeriodCalculator.tsx:145-168` — 세 세트 모두 **조건 분기 없이 항상 렌더**.
  `{result.years}`가 `0`이면 `0`이 그대로 출력된다(JSX에서 숫자 0은 falsy 스킵 대상이 아님). [확인]
- 보조값도 동일: `약 0.0년`(소수 근속연수)은 `toFixed(1)`로 후행 0 유지(`:195`), 스펙 §5(299-301행)와 일치. [확인]

### 2-2. "빈 문자열이 되지 않는가" — 구조적으로 불가능

전부 생략하는 규칙 자체가 없으므로 **전부 0인 경우의 빈 문자열 fallback 규칙도 불필요하다.**
참고로 입사일 당일 퇴사는 양 끝 포함(+1) 규칙상 `총 1일 / 0년 0개월 1일`이 되고
(`design\...ui-spec.md` 앵커 E), 세 자리가 모두 0이 되는 입력은 **존재하지 않는다.**
(엔진이 `end < start`를 `end-before-start` 에러로 먼저 막고 — `lib\service-period.ts:67-69` —
최소값이 1일이기 때문. [확인])

### 2-3. 개발팀에 대한 유일한 요청: **"수정하면서 0 생략을 끼워 넣지 말 것"**

borrow 버그를 고치다 보면 `0년`이 자주 등장하는 게 어색해 보여 조건부 생략을 넣고 싶어질 수 있다.
**넣지 말 것.** 이유:

- 히어로는 "숫자 크게 + 단위 작게" 3세트 고정 위계다. 자리 수가 입력마다 1~3개로 변하면
  대표값 블록의 크기·정렬이 결과마다 출렁여 스캔 비용이 커진다.
- `0년 0개월 5일`은 "5일밖에 안 됐다"는 정보를 **명시적으로** 전달한다. `5일`만 남기면
  사용자는 "년/개월이 계산 안 된 건가?"로 오해할 여지가 생긴다(계산 실패와 구분 불가).
- 회귀 테스트 앵커(`scripts\regression\engines.test.ts` service-period 스위트)가 3부분 값을 전제한다. [확인]

## 3. 방어적 표시(음수 방어 렌더링) 판단

**질문:** 엔진 수정 후에도 UI가 음수를 받으면 어떻게 할 것인가?

### 3-1. 찬성 논거

- 근속기간은 **동일 엔진이 퇴직금 계산기까지 먹이는 공유 자산**이다(§1-2). 향후 다른 계산기가
  재사용할 때 상류 변경이 하류 화면을 다시 깨뜨릴 수 있다.
- 이번 결함은 **9일 넘게 라이브에 노출된 뒤 브루트포스로야 발견**됐다. 화면 스스로는 이상을
  알리지 않았다. 표시부에 감지 장치가 하나도 없다는 뜻이다.
- 음수 일수는 사용자에게 **의미가 0인 출력**이다. 어떤 해석도 불가능하다.

### 3-2. 반대 논거 (더 무겁다)

- **"UI에서 음수를 숨기자"는 근본 수정을 가리는 안이다.** `Math.max(0, days)`나 `Math.abs(days)` 같은
  클램프를 넣으면 `26년 1개월 -1일`이 `26년 1개월 0일`로 바뀌어 **화면상 정상처럼 보이지만
  값은 여전히 틀렸다.** 이번엔 음수라는 눈에 띄는 증상 덕에 발견됐는데, 클램프를 넣으면
  다음 유사 버그는 **영영 발견되지 않는다.** 계산이 틀렸는데 화면만 가리는 건 지금보다 나쁘다.
- 사용자 관점에서도 "틀렸지만 그럴듯한 숫자"가 "명백히 이상한 숫자"보다 위험하다.
  근속기간은 퇴직금·연차 판단의 입력값이라 조용한 오차가 실제 손해로 이어질 수 있다.
- 회귀 테스트가 이미 존재한다(`scripts\regression\engines.test.ts`). 방어선은 **엔진 쪽에서**
  치는 게 맞고, 표시부 클램프는 그 테스트마저 무력화한다.

### 3-3. 권고 (디자인팀 결론)

**결론: 표시부에 값 클램프(`Math.max(0, ...)`, `Math.abs(...)`, 음수 시 대체 문구)를 넣지 않는다.
현재의 "엔진 값 그대로 표시"를 유지한다.** — 즉 **표시 규칙 변경 없음.**

권장 대안은 **화면을 조용하게 만드는 방어가 아니라, 값을 못 내보내게 하는 방어**다.
아래는 개발팀 판단 사항으로 넘긴다(디자인팀은 UI 영향만 명시):

- (권장) `lib\service-period.ts` 내부에서 분해 결과가 `days < 0 || months < 0` 이면
  **개발 환경 콘솔 경고 또는 테스트 실패**로 드러나게 한다. UI 표시는 건드리지 않는다.
  → 화면 영향 **없음**. 디자인 검수 불필요.
- (권장) borrow를 `while`/정합 검증 방식으로 고친 뒤, 음수 발생 조합(월말 입사 + 짧은 달 종료)을
  **회귀 테스트 앵커로 추가**한다. 브루트포스 33건 중 대표 3~5건이면 충분.
  → 화면 영향 **없음**.
- (비권장) 결과 카드에 "계산 오류" 배너를 띄우는 방식. 확정 스펙 §3-4는 오류를 **입력 필드 하단
  인라인**으로 처리하고 결과 영역 배너는 사이트 전체에 없는 언어라 도입하지 않기로 이미 정했다
  (`design\...ui-spec.md` 265-268행). [확인] 정상 동작에서 절대 안 보일 UI를 새로 만드는 건
  비용 대비 이득이 없다.

   `2000-01-31 ~ 2026-03-01`(최장 케이스) 입력. 히어로가 **한 줄**인지, 줄바꿈됐다면 어디서 끊기는지.

2. **0 값 3종 렌더 실물 확인** — `0년 0개월 5일` / `1년 0개월 0일` / `0년 3개월 0일`이
   0 생략 없이 그대로 나오는지. 요약 문구(§1-1 C)와 히어로(A)의 값이 **서로 일치**하는지.
3. **입사 당일 퇴사** — 입사일=퇴사일 입력 시 `총 1일 / 0년 0개월 1일 / 약 0.0년`인지.
4. **퇴직금 계산기 동반 확인 (중요)** — `/calculator/severance-pay-calculator`에 같은 날짜를 넣고
   `재직일수 ... (근속 N년 M개월)`의 **개월 값이 근속기간 계산기와 일치**하는지.
   두 화면이 서로 다른 개월 수를 보이면 수정이 절반만 반영된 것입니다.
5. **스크린리더/DOM 확인(가능하면)** — 히어로 `aria-label`(`:143`) 문자열에 음수가 남아 있지 않은지.
   개발자도구에서 해당 `<p>`의 `aria-label` 속성값만 봐도 충분합니다.
