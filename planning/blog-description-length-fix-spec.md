## §1 배경·목적

### 1-1. 왜 160자인가
블로그 35편 중 8편의 `description`이 160자를 넘는다(최장 196자). 구글 SERP 스니펫은 데스크톱 기준 대략 155~160자에서 잘리므로, 초과분은 **표시되지 않는 채로 문자열만 길어진 상태**다. 07-22 GSC 감사에서 티켓 #3(낮음)으로 최초 제기되었고 07-23·07-25 감사에서도 미해소로 유지되었다. 07-24에 승격된 `title ≤ 51자` lint와 동일한 성격의 후속 정정이다.

### 1-2. 이 필드가 쓰이는 곳 (3곳, 전부 코드 무수정으로 함께 고쳐진다)
| 소비처 | 파일 | 성격 |
| --- | --- | --- |
| `<meta name="description">` | `app/blog/[slug]/page.tsx` L37 `generateMetadata` → `description: post.description` (접미사 없이 원문 그대로) | 비가시 SEO. SERP 스니펫 원본 |
| 블로그 목록·카테고리 카드 요약 | `components/BlogPostCard.tsx` L34~35 `<p className="line-clamp-2 …">{post.description}</p>` | **화면에 보이는 가시 카피.** `line-clamp-2`라서 앞 2줄만 노출 |
| BlogPosting JSON-LD | `lib/blog-jsonld.ts` L36 `description: post.description` | 구조화 데이터 |

즉 이 한 줄은 **SEO 메타이자 동시에 카드 UI 본문**이다. 그래서 이번 정정의 목표는 단순 자르기가 아니라 "앞 2줄 안에 핵심이 들어오는 짧은 완결문"이다.

### 1-3. 목표
- 8편 전부 `[...description].length` 기준 **135~155자**(절대 상한 158자).
- 사실 재검증 부담 0: 새 숫자·새 주장 도입 금지 → 원문이 통과한 QA 결과를 그대로 승계한다.

## §2 정정 원칙 (지시 ①~⑥의 재진술)

1. **숫자 무증식.** 정정본의 모든 숫자 토큰은 원문 description 숫자 토큰의 **부분집합**이어야 한다. 본문·엔진에서 새 수치를 끌어오지 않는다. 삭제는 되고 추가는 안 된다. → 원문이 이미 검증된 문장이므로, 삭제·압축만 하면 사실 검증이 자동 승계된다. 새 숫자를 하나라도 넣으면 계산 엔진 재검산이 필요해져 이번 회차 범위를 벗어난다.
2. **삭제·압축·재배열만.** 허용: 무정보 수식어 제거(`실제 예시로`, `바로`, `한눈에`, `크게` 등), 조사 정리(`~부터 ~까지` → `~`), 문장 순서 바꾸기, CTA 축약. 금지: 원문에 없는 주장·형용·판단 추가.
3. **YMYL 판정성 표현 0건.** "유리합니다 / 이득입니다 / 해야 합니다" 류 단정 금지. 원문의 의문형 훅("~일까요?")과 완충어("약", "달라집니다")를 그대로 유지한다. 금액·요율 앞의 `약`은 절대 지우지 않는다.
4. **핵심 키워드 보존 + 앞 60자 배치.** 스니펫 앞부분 가중치 + 카드 `line-clamp-2`(앞 2줄만 보임) 두 이유로, 각 글의 주 키워드를 앞 60자 안에 넣는다. 미달 시 §3에 그 사실을 그대로 적는다(숨기지 않는다).
5. **CTA 문장 유지.** "~계산기로 내 ~도 확인해 보세요" 류 내부링크 유도 카피는 축약은 하되 삭제하지 않는다. 축약한 편은 §4 표에 `축약`으로 표기한다. (단 #6은 원문에 CTA가 애초에 없다 → `해당없음`.)
6. **문형 수렴 회피.** 8편이 같은 틀로 수렴하면 스니펫 중복으로 보인다. 도입부 형태를 의도적으로 분산했다: 상황 질문형(#1) / 대조 제시형(#2·#7) / 현상 설명형(#3) / 독자 상황형(#4) / 개념 구분 질문형(#5) / 금액 질문형(#6) / 공식 질문형(#8).

### 계수 방법(중요)
아래 모든 자수는 **문자 단위로 직접 센 값**이다(공백·문장부호·`·`·`−`·`~`·`%` 전부 1자). 검증 삼아 원문 8편을 먼저 세었고 **8편 모두 마스터 지시서의 자수(196/185/173/171/170/169/164/163)와 일치**했다 → 같은 방법으로 센 정정본 자수도 동일 신뢰도로 본다. 이식 후 dev-team이 `[...s].length`로 재확인하면 §4 표와 일치해야 한다.

**정정 후 (151자)**
```
대출을 갈아탈 때, 중도상환수수료를 물고도 이득일까요? 손익은 '이자 절감액 − 중도상환수수료'입니다. 잔액 1억원·10년 기준 금리 인하폭별 이자 절감액과 경과기간별 수수료를 2026년 표로 정리했습니다. 대출 이자·중도상환수수료 계산기로 내 손익분기를 확인해 보세요.
```

- 삭제/압축: `금리가 내려`·`남은` 삭제, `기준으로`→`기준`, `2026년 기준 표로`→`2026년 표로`, `로 결정됩니다`→`입니다`. 후반 절차 안내(`계산기를 각각 돌려 … 직접 확인하는 3단계 방법을 안내합니다`)를 `계산기로 내 손익분기를 확인해 보세요`로 축약하고, 계산기 두 개를 `대출 이자·중도상환수수료 계산기`로 병렬 압축.
- 숫자 토큰 대조: 원문 `1억원 / 10년 / 2026년 / 3단계` → 정정본 `1억원 / 10년 / 2026년`. (3단계 삭제, 신규 0)
- 보존 키워드: 중도상환수수료(12자, ✔ 앞 60자) · 이자 절감액(✔) · 대출 갈아타기(`대출을 갈아탈 때`, 1자, ✔) · 손익분기.
  ⚠ **`손익분기`는 138자 지점으로 앞 60자 밖**. 앞부분에는 원문 표현 `손익은`(32자)이 있다. `손익은`을 `손익분기는`으로 바꾸면 "손익분기 = 절감액 − 수수료"라는 부정확한 등식이 되므로(손익분기는 그 값이 0이 되는 지점) 바꾸지 않았다. **사실 정확성을 우선한 의도적 미충족**이며 8편 중 유일한 앞 60자 규칙 예외다.
