### 0-4. 이 글의 고유 프레임
"한 회사 한 구간"이 아니라 **여러 구간의 합산**. 기존 2편이 설명한 +1·윤년 원리를 되풀이하지 않고(형제글로 넘김), 합산 단계에서만 발생하는 4가지 함정을 다룬다.
1. `N년 M개월`끼리 더하기 → 성립하지 않음('1개월'의 길이가 가변)
2. 반올림된 소수 근속연수끼리 더하기 → 중간 반올림 누적 오차
3. 첫 입사일~마지막 퇴사일 **통합 계산** → 공백기간이 경력으로 섞여 과대 계상
4. 퇴사일 = 입사일이 겹치는 경우 → 하루 이중 계상

부수 효과: 계산기를 **구간 수만큼 반복 사용**하게 되므로 세션당 계산기 조작 횟수·체류시간이 늘어난다(단일 조회형 글보다 유리).

## §3. 근거 lib 함수와 재검산 대상 셀

### 3-1. 근거 함수

| 본문 값 | 근거 파일 | 함수 | 규약 |
|---|---|---|---|
| 재직일수 | `lib/service-period.ts` | `calculateServicePeriod()` (L45) | `totalDays = daysBetween(입사일, 종료일+1일)` = (종료일−입사일)+1, 양 끝 포함 |
| 근속기간 N년 M개월 D일 | `lib/service-period.ts` | 같은 함수 (b) 블록 L84~101 | 입사일 → 종료일⁺ 캘린더 분해, 부족분은 종료일⁺ **직전 달의 실제 일수**를 차용(윤년 자동 반영) |
| 소수 근속연수 | `lib/service-period.ts` | 같은 함수 (c) 블록 L104 | `Math.round((totalDays / 365) * 10) / 10` — 소수 첫째 자리 반올림 |
| 공백일수 | 동일 함수 재사용 | `calculateServicePeriod("퇴사 다음날","입사 전날")` | 근무 구간과 동일하게 양 끝 포함 |

반올림 규약 준수: 본문의 연 단위 환산은 **합계 일수를 낸 뒤 마지막에 1회만** 나눈다(§2 [19][22][23]). 중간 반올림값(소수 근속연수)을 더하는 방식은 본문에서 **반례로만** 등장하며 권장하지 않는다. 이는 `annual-leave-allowance.ts` 주석의 라운딩 원칙(중간 전 정밀도 유지, 표시값만 반올림)과 동일한 방향이다.

### 3-2. ⚠ 자진 보고 — 본 스펙의 수치는 전부 손 유도값

### 3-4. ⚠ 별건 보고 — `calculateServicePeriod` 월말 입사일 경계 결함 (본 기획과 무관, 발견 사항)

본문 수치를 유도하며 lib를 읽던 중 발견. **본 36편이 이 경로를 밟지 않는 정확한 근거는 아래 3-4-1에 적었다.** (QA 1차 N2 정정 — 종전 서술 "예시의 입사일을 전부 28일 이하로 고정했다"는 **사실이 아니다.** §2 [35]에 입사일 `2026-03-31`이 있다.) 결함 자체는 별건으로 남긴다.

`lib/service-period.ts` L88~101은 `days < 0`일 때 직전 달 일수를 **한 번만** 빌린다. 입사일의 일(day)이 29~31이고 종료일이 월말이면 보정 후에도 `days`가 음수로 남는다.

- 입력: `calculateServicePeriod("2026-01-31", "2026-02-28")`
- 추적: `endPlus = 2026-03-01` → `months = 2−0 = 2`, `days = 1−31 = −30` → 차용 `new Date(2026,2,0).getDate() = 28`(2026년 2월) → `days = −2`, `months = 1` → **`days`가 여전히 음수인 채 반환**
- 예상 화면 표시: `0년 1개월 -2일`

`totalDays`(=29)는 정상이고 근속기간 표시만 깨진다. 손 추적 결과이므로 **개발팀 재현 확인이 필요**하며, 판단·수정 착수 여부는 마스터에게 맡긴다(기획팀은 코드를 고치지 않는다).

#### 3-4-1. 본 36편이 이 경로를 밟지 않는 이유 (QA 1차 N2 정정)

§2의 입사일 중 29일 이상인 것이 **1건 있다** — [35] 다음 회사 `2026-03-31`(나머지 입사일은 전부 1~13일). 종전의 "전부 28일 이하" 서술은 오기이며, 실제 안전 근거는 다음 둘이다.

1. **엔진 추적상 음수가 나오지 않는다(경계에 0으로 착지).** `calculateServicePeriod("2026-03-31","2026-04-30")` → `endPlus = 2026-05-01`(4월은 30일까지라 `new Date(2026,3,31)`이 5월 1일로 넘어감) → `days = 1 − 31 = −30` → 차용값 `new Date(2026,4,0).getDate()` = **2026년 4월 = 30** → `days = 0`, `months = 2 − 1 = 1` → **`0년 1개월 0일`**. 차용 후 `days`가 음수로 남지 않으므로 결함 경로에 해당하지 않는다. `totalDays`도 31로 §3-3 셀 18과 일치한다.
2. **표시 경로 자체가 없다(이중 안전장치).** [35]의 다섯 줄은 일수만 적고 `N년 M개월 D일`을 한 번도 표기하지 않는다. 설령 1이 깨져도 화면에 나올 값이 아니다.

**재현 조건도 함께 정정한다.** 종전 조건(`종료일 다음 달 직전 달 길이 < 입사일의 일`)은 위 [35] 케이스를 **오탐**한다(30 < 31이 참이지만 실제로는 안전). 코드 L86~97 그대로의 조건은 다음과 같다.

- 음수 잔존 ⇔ `(종료일⁺의 일 − 입사일의 일) + (종료일⁺ 직전 달의 일수) < 0`
- 종료일이 월말이면 `종료일⁺의 일 = 1`이고 `종료일⁺ 직전 달 = 종료월`이므로 → **`종료월의 일수 < 입사일의 일 − 1`**
- 대입 검증: 결함 예시 `2026-01-31 ~ 2026-02-28`은 `28 < 30` 참 → `−2일`. 본문 [35]는 `30 < 30` 거짓 → 안전.

## §6. 마스터 확인 요청 (기획팀 단독 판단하지 않은 사항)

1. **수치 재검산 (필수)** — §3-3 20셀 + 부수 3건. Bash 부재로 손 유도. dev 착수 전 엔진 실행 검증 요청. 교차검산 2쌍(2,929+135=3,064 / 61=61)부터 보면 빠르다.
2. **자수 재측정 (필수)** — title 38자·description 146자 자기보고. 07-25 선례 재발 방지.
3. **§3-4 lib 결함 보고 (별건)** — `calculateServicePeriod`가 월말 입사일에서 음수 일(日)을 반환할 수 있음(손 추적). 본 36편은 회피했으므로 발행을 막지 않는다. 개발팀 재현 확인 대상으로 넘길지 마스터가 판단해 주기 바란다.
4. **date 클러스터 다음 회차 방향(참고)** — 이번으로 date 9편, service-period 계열 3편이 된다. 다음 date 회차는 dday·service-period 모두 포화이므로 **annual-leave 계열 2편째**(회계연도 기준 부여) 또는 **date 신규 계산기 도입**이 필요하다. 전자는 법 해석 비중이 커 YMYL 상향 위험이 있어 기획팀 단독으로 정하지 않고 남긴다.
